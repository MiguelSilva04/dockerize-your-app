# Measurements: original vs improved

Working rules: measure the original before touching anything. One change at a time. Measure after each change. Write down what did not improve too.

Measurement conditions: original image built from commit `9715fef`, Docker Desktop on Windows, stack started with `compose.yml` only (without the override) and with the session's own secrets. The `baseline` tag (`c34e874`) has the same Dockerfile, and the only difference is the removed `.github` folder. Saved images: `backend:baseline` (original), `backend:nodev` (change 1), `backend:slim` (change 2, which includes 1), `backend:nonroot` (change 4, which includes the previous ones), `backend:nonroot-newbase` (the same one-stage image, rebuilt on the new base) and `backend:multistage` (change 5). Changes 3 and 6 have no image of their own: 3 is only in `compose.yml` and 6 only in `.dockerignore`.

The `python:3.14-slim` tag moved between change 4 and change 5, from 3.14.9 (digest `35caba83...`) to 3.14.10 (digest `82abc9f5...`). It moved again during change 6 (digest `9aaa4740...`, Python version 3.14.10, same as the previous one). That is why change 5 is compared against `nonroot-newbase`, and change 6 is compared using two builds on the same base.

CPU and memory protocol: fresh stack, 6 minutes after the backend started (confirmed with `docker compose ps`) and three `docker stats --no-stream` samples 30 s apart. Measurements taken before the protocol are marked as such and are not comparable with each other.

Change 7 (compose): starting state at commit `82a2321`, image `backend:latest` with ID `119fffb035ea` (the multi-stage one), session secrets, stack started with only `up -d backend` on an empty database (`down -v --remove-orphans` before) and always with `-f compose.yml`. The `compose.yml` had no service that ran the migrations. The final `compose.yml` is at commit `afca1c8`. Two attempts to measure the "before" were invalid and were repeated: the first in a terminal without the secrets (compose took `changethis` from `.env` and the backend exited with `Exited (1)`, because the app refuses the default `SECRET_KEY`), the second without `-f compose.yml` (the `compose.override.yml` was loaded, with `fastapi dev` and published ports).

## Initial hypothesis

Initial prediction: the size came from the Python dependencies.

Measured result: most of the original image's size comes from the `python:3.14` base image (about 1.2 GB, 76% of the layer total), because it includes compilers, development libraries, git and other tools the app does not need to run. The dependencies installed by uv are the 319 MB layer (about 20%).

## How to read each value

**Size on disk and compressed content.** "On disk" is what the image takes up uncompressed in your Docker. "Compressed content" is roughly what travels in a push or pull. Always compare disk with disk, using the same tool. When the base tag moves (like `3.14-slim`), the reference image has to be rebuilt on the new base, otherwise the comparison mixes two things. The layer percentages are of the layer total.

**Layers.** Each Dockerfile instruction creates a layer, and the size is what that instruction wrote to disk. `docker history` reads from bottom to top. The bottom layers come from the base image and are not the template's. In the full image, the 695 MB are compilers and development libraries, the 202 MB are git, mercurial and subversion, the 65 MB are utilities such as `curl`, and the 83.3 MB are the compiled Python. The sum of the layers is below the on-disk size in `docker image ls` in every image (about 1.57 GB against 2.11 GB for the original, 333 MB against 439 MB for the non-root one, 279 MB against 362 MB for the multi-stage one), and I cannot explain why.

**Multi-stage.** A Dockerfile with several `FROM` lines. The final image is only the last stage, and it carries only what is copied from the earlier ones with `COPY --from`. Here, the `builder` stage has `uv` and installs the dependencies, and the `runtime` stage receives only the environment (`/app/.venv`), the code and the compiled frontend. The `uv` binary stays in the discarded stage, which is where the 53.2 MB saving comes from. There are three things to watch. The `.venv` points to the Python that created it, so both stages start from the same base. The `app` package is installed in editable mode, pointing to `/app/backend`, so the code has to be at that path in the final stage. And the `ENV`, `WORKDIR`, `USER` and `CMD` instructions do not carry over from one stage to the next. The `builder` also needs the code in `app` and the `pyproject.toml`, for `uv sync` to install the package.

**Build context.** The set of files that `docker build` hands to Docker, the folder given as the last argument of the command. The `.dockerignore` that counts is the one at the root, because the context is the root. `backend/.dockerignore` and `frontend/.dockerignore` would only count if the context were `backend/` or `frontend/`. The `transferring context` number in the log is incremental, only what changed since the last build, so it cannot be used to compare. The measure used is the `du` of a `COPY . /ctx` in a throwaway Dockerfile. In this repo the Dockerfile only copies specific paths, so excluding files does not change the image. In a project with `COPY . .`, everything the `.dockerignore` does not exclude goes into the image, and the `.env` experiment shows it: with the old file `.env` gets in, with the new one it does not.

**Python packages.** The 14 that left with `--no-dev` were: ast-serialize, coverage, iniconfig, librt, mypy, mypy-extensions, packaging, pathspec, pluggy, prek, pytest, ruff, ty and zizmor. Some are dependencies that only the development packages used.

**User.** `uid=0` is root. If the app is compromised, the attacker starts with root privileges inside the container. With a non-root user, the process cannot change the app code, and the `touch` test shows the refusal. In Kubernetes, the `runAsNonRoot` option needs to be able to verify that the image's user is not root, and for that the image's `USER` should be a number (to be confirmed in the Kubernetes documentation). That is why `USER` is `10001:10001`, and `useradd` only exists so the uid has a name (`appuser`) for whoever debugs the image.

**Build times.** The clean one mixes image downloads with build work and depends on the network. The 2.3 s one is the floor, with everything cached. The 2.9 s one from change 4 shows what happens when only the last layers change, and it is why `useradd` is near the end of the Dockerfile. The other builds have partial cache, so they are not comparable with each other.

**Idle CPU and memory.** These are samples without load, and the `CMD` starts 4 workers, so the memory includes the 4 processes. Memory varies even within one run: one of the original's samples dropped 13 MiB in 30 seconds. For the original the memory ranged from 476.4 to 493.2 MiB, and for the non-root image from 499.0 to 504.8 MiB. At 6 minutes, the medians are about 487 and 499 MiB, a difference of about 12 MiB (2%) that is smaller than the spread between samples of the original. With so few runs it is not attributed to the image. CPU jumps between samples (there was a peak of 13.78%), so the range is recorded. The processes (PIDs) are 10 at 6 minutes in both images, and 11 in the samples at 33 minutes and in some earlier ones. I do not yet know what the extra process is.

**Healthcheck.** The healthcheck runs a command inside the container every 10 seconds. An error like `executable file not found` means the command did not even start. The new one uses Python's `urllib`, which is already in the image, and fails with code 1 when the connection is refused. The restart counts were always 0 while `compose.yml` defined no restart policy (change 7 adds one). The exit code only matters when the process ends. The health endpoint only returns `true` and does not touch the database, so it is the login through the API that proves the database and the password check work.

**`import app` from `/`.** The image's working directory is `/app/backend`, and Python puts the current directory on the search path, so an `import app` done there would work even if the editable mode were broken. With `-w /`, the current directory no longer helps, and the import only works if the `.pth` pointer from the `.venv` to `/app/backend` is working.

**Compose.** `depends_on` with `condition` makes compose wait for the state of another service: `service_healthy` waits for the database to answer its healthcheck, and `service_completed_successfully` waits for a one-shot service to end with code 0. That is why `prestart` runs before the backend on every `up`, and why a failing `prestart` leaves the backend in `Created`. The `unless-stopped` policy restarts the container when it stops, without looking at the exit code (according to the Docker docs, only on-failure is tied to a non-zero exit code; this was not tested with prestart), and respects a manual stop. That is why `prestart`, which exits on purpose, has `restart: "no"`. `start_period` gives a grace period at startup, during which healthcheck failures do not count towards the retries. A service with `profiles` only starts when the profile is requested (`--profile tools`). Without `-f compose.yml`, compose merges `compose.override.yml` into the base file, which is the upstream development setup.
